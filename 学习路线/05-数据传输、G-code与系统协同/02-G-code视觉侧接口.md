# G-code 视觉侧接口

G-code 在这里是视觉结果与机械动作之间的文本接口：视觉端把已经标定的机械坐标和动作顺序写成一串命令，交给执行端解释并驱动机械。本篇讲视觉侧怎样生成和发送这些命令；解释器内部怎样驱动电机，是控制同学的内容。

## G-code 从哪里来，谁在执行它

G-code 是数控机床（CNC）使用的运动控制语言，后来被 3D 打印机固件（Marlin、GRBL 这一族）沿用，是嵌入式运动控制里最常见的一套现成命令集，这是一套新的控制方式区别于学习的STM32，他的优势体现在对较大机械结构的控制上，如解决2024年三子棋、2026年拼图装置这类型的题目，同时他属于视觉手的额外学习部分，你可以将转换后的世界坐标直接发送给控制手进行切换，甚至可以只发送像素坐标交给上位机进行转换与计算。

学习到这里的你需要理解“系统”的概念，摄像头解决图像的采集问题、机械解决执行问题，但是核心的计算与调度需要一个高算力的“芯片”上位机来控制，也就是说只认为 MaixCAM 是视觉、STM32等芯片是控制“过时了”，而是构建起上位机与下位机的概念。学习到这一步不能简单的区分视觉手、控制手、机械手等单一标签，而是整个系统的某一模块的负责人，你们出现了界限不是那么明确的事情需要更多的协商讨论，如坐标标定、控制逻辑指令生成应该在哪里生成（依旧使用 MaixCAM 这样的产品前提下）

G-code 是一行一条命令、纯文本，每条命令由字母加数值地址组成：

```text
G1 X261.000 Y231.000 F3000
│  │         │         └─ 进给速度，单位 mm/min
│  │         └─ Y 轴目标位置，单位 mm
│  └─ X 轴目标位置，单位 mm
└─ 直线移动命令
```

用电赛的话说，使用 G-code 的前提是接收端有一个解释器，常见两种来源：

1. 控制端使用 CNC／3D 打印机类现成固件（Marlin、GRBL 等）。固件把 `G1` 翻译成步进电机运动，把 `M` 系命令交给配置好的外设。
2. 控制队友自己写解析器，按双方约定的语义执行收到的文本。

我们当初选择的是 Marlin 固件进行解析执行，实际下位机内部是哪种实现，以控制同学为准，并且非常建议提前学习了解。视觉端的责任是保证发出的文本符合双方约定，语义不明的命令逐条确认。

这个分工正是 G-code 接口的价值：视觉端不需要懂电机和驱动，控制端不需要懂图像，中间传递的只有文本语义。

## 先认识这组命令

### 数控标准里的通用移动命令

| 命令                 | 含义                                 | 拼图题目示例                      |
| -------------------- | ------------------------------------ | --------------------------------- |
| `G90`                | 此后坐标按绝对位置解释               | 每段动作开头                      |
| `G91`                | 此后坐标按相对位移解释               | 未使用；知道它与 `G90` 的区别即可 |
| `G1 X.. Y.. Z.. F..` | 以进给速度直线移动到目标点           | 所有移动                          |
| `G4 P500`            | 原地暂停 500 ms                      | 等吸附、等舵机到位                |
| `G92 X0 Y0 Z0`       | 把当前位置定义为给定坐标，不产生移动 | 仅上电时建立一次原点              |

两个容易出错的细节：

- `F` 的单位是 mm/min，不是 mm/s。拼图题目代码默认 `F3000`，即 50 mm/s；发送端的执行时间估算也按除以 60 换算成 mm/s。
- `G92` 改写的是坐标基准。示例代码只在上电序列发一次；标定用的 `calib_move()` 特意不再发它，代码注释写明原因——原点由上电序列统一建立，避免重复建立原点后移动累积跑偏。在动作中途随手发 `G92`，会把已经对好的坐标系悄悄搬走。

### 固件扩展命令（不是通用标准）

`M400`、`M106`、`M107`、`M280` 来自 Marlin 类 3D 打印机固件的 `M` 系扩展：

- `M400`：等之前排队的移动全部完成再继续。Marlin 有这条，别的解释器未必有。
- `M106 S255`／`M107`：固件本义是风扇全开／关闭；示例代码中把这路输出接到电磁铁，用作吸附和释放。
- `M280 P0 S90`：0 号舵机转到绝对角度 90°。

这四条的含义依赖控制端的固件配置和接线。2026 拼图题目中它们承担吸附和旋转动作，但移植到其他队伍的控制系统时，必须让接收端逐条确认，不能当通用标准直接发送。

## 什么情况下适合使用 G-code

G-code 适合把已经确定的机械坐标和动作顺序，交给一个明确支持 G-code 的执行端。判断条件：工件固定在同一工作平面上；相机与机械坐标已经标定并经已知点校验；视觉给出稳定的取放点；后续动作可以枚举成有限的移动、等待和项目专用动作。2026 拼图正是这种形态——识别和求解完成后，剩下的就是一组确定的取放序列。

它不适合直接处理持续变化的画面。目标在移动、机械需要实时避障或力控、相机位置未固定、坐标误差还没有验证时，视觉端不应根据单帧结果生成并发送动作；这些场景需要的是连续测量加实时闭环，见[视觉结果与 PID 协作](03-视觉结果与PID协作.md)。

还要清楚 G-code 不提供什么：它只是命令文本，不会告诉视觉端"机械是否真的到位"。是否重发、要不要等状态反馈、急停和限位由谁处理，必须由系统接口另行约定。

因此本路线把"能够生成 G-code"放在最后：先验证检测和标定，再用日志检查命令，最后才接真实机械。G-code 不是跳过标定、轨迹规划和安全确认的捷径。

## 从像素到动作：一次完整翻译

整体流水线是：

```text
检测中心 (u,v)
→ 坐标标定得到机械坐标 (x,y)
→ 生成 G1 移动文本
→ 加入 M400/G4 组成完整动作块
→ EEEF/FFFE 包围动作块
→ 按节奏逐块发送
```

2026 的生成逻辑在 [gcode_generator.py](../../配套资源/历年题目参考代码/2026-拼图视觉/gcode_generator.py)。一次"抓取 → 旋转 → 放置"生成的完整命令如下，坐标数值为示例，由[坐标标定](../04-坐标转换、标定与现场调试/01-坐标标定.md)的映射从像素算出：

```text
G92 X0 Y0 Z0                 上电：当前位置定义为原点
G90                          绝对坐标模式
G1 Z-1.0 F3000               抬到安全高度（2026 配置中安全高度为 -1、工作高度为 0，Z 正方向由机械定义）
G4 P500
M280 P0 S90                  舵机回初始角度
G1 X261.000 Y231.000 F3000   移动到碎片上方：像素 (340,244) 经映射得到 (261,231)
M400                         等移动完成
G1 Z0.0 F3000                降到工作高度
M400
M106 S255                    电磁铁吸附
G4 P500                      等吸附稳定
G1 Z-1.0 F3000               抬起
M400
M280 P0 S105.000             舵机转 15°（初始 90° + 15°）
G4 P500
G1 X243.000 Y261.000 F3000   移动到目标格上方
M400
G1 Z0.0 F3000
M400
M107                         释放
G4 P500
G1 Z-1.0 F3000               抬起
M400
M280 P0 S90                  舵机归零：下一片从固定角度开始
G4 P500
```

生成器把动作组织成可复用的方法：`start_gcode()` 建立原点和初始姿态；`pick_place_rotate()` 按"移动 → 降 → 吸 → 升 → 旋转 → 移动 → 降 → 放 → 升 → 归零"组合一个碎片；`end_gcode()` 抬高回零。视觉端的工作只有两件：给出可信的像素坐标，把动作顺序翻译成这类文本。

两个设计细节：

- 旋转量超过舵机 ±90° 行程时，`rotate()` 自动把动作拆成"转到行程极限 → 放下 → 松开 → 舵机回零 → 重新吸取 → 转剩余角度"。机械能力不够时用动作序列补足，而不是发一条执行不了的命令 -- 当时组内使用的舵机最大旋转角为 90。
- 每次放置后舵机都归零。`M280` 是绝对角度指令，归零保证每片的起始角度相同；多两条指令，换取确定性。

## 为什么要分块、按节奏发送

上面那段动作有二十多条命令。一次全部写入串口，不等于接收端能缓存并执行：解释器的命令缓冲有限，灌满后丢命令，动作就错乱。2026 的 [my_utils.py](../../配套资源/历年题目参考代码/2026-拼图视觉/my_utils.py) 用"分块 + 滴灌"解决：

1. 按 `M400` 或 `G4` 把命令流切块。同步指令天然是一个语义单元的结尾，移动和属于它的 `M400` 绝不拆开。
2. 每块用 `EEEF\r\n` 和 `FFFE\r\n` 包围成文本包，格式背景见[串口数据格式](01-串口数据格式.md)。
3. 发一块，等一块。等待时间 = 该块估算执行时间 × 1.5 + 400 ms。估算规则：`G1` 按移动距离÷速度，`G4` 按暂停时长，`M280` 按舵机角度差 × 每度 5 ms。
4. 任何时刻接收端缓冲里最多积压一块，缓冲再小也不会爆。

## 安全调试顺序

1. 只生成文本并保存日志，不打开串口。
2. 人工检查绝对/相对模式、单位、原点、速度，以及坐标是否都在机械工作范围内。
3. 串口回环验证帧头、帧尾和换行。
4. 接收端只解析，不驱动机械。
5. 机械上电后先限制速度和工停方式。

教学示例 [gcode_demo.py](../../配套资源/示例代码/通信与gcode/gcode_demo.py) 固定执行第一步：把像素点和标定参数写在文件开头的调参区，运行后只打印分块后的帧文本，不打开串口：

```powershell
python 配套资源\示例代码\通信与gcode\gcode_demo.py
```

## 这套接口容易在哪里出错

- 方向镜像：轴交换或符号错误会让机械走向镜像位置。`gcode_generator.py` 的做法是用多点校验发现上下/左右镜像后，翻转 `x_sign`／`y_sign`，校验方法见[坐标标定](../04-坐标转换、标定与现场调试/01-坐标标定.md)。
- 中途改原点：见上文 `G92` 一节，动作序列中途不要碰坐标基准。
- 把固件扩展当通用标准：`M` 系命令逐条与接收端确认。
- 忽视 Z 方向约定：安全高度是正是负、抬是 Z 增还是 Z 减，由机械定义（2026 的安全高度是 -1）。双方没在同一张图上确认过 Z 方向之前，不要发 Z 命令。
- 依赖不存在的反馈：发出 `G1` 后机械是否真的到位，G-code 文本本身不回答。2026 用 `M400` 加估算时间做开环节流；到位确认和异常处理属于系统接口层要另行约定的事。
