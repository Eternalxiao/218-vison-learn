# 串口数据格式

## 串口传的是字节流，不是一条条消息

视觉程序发送数据通常只是一行调用：

```python
serial.write_str('{"x": 12.5}')
```

这行代码背后发生的事：字符串先被编码成一串字节，再一个字节一个字节地移出引脚。接收方调用读取时，拿到的是“这一瞬间已经到达、还没被读走的若干字节”——可能是半条消息，也可能是两条半。

“一条消息”这个概念，串口硬件本身没有。它是发送方和接收方之间的约定：字节流里从哪里到哪里算一条、字段按什么顺序、每个字段几个字节。约定没写清就开写代码，联调时表现出来的就是“数据时对时错”：解析偶尔对上、偶尔错位，很难复现。

所以这一章的顺序是：先定接口约定，再选编码格式，最后写带缓冲区的解析。波特率和编码也属于约定：两边波特率不一致，收到的是错位字节；教学示例 [`protocol.py`](../../配套资源/示例代码/通信与gcode/protocol.py) 里两种文本分别用 ASCII 和 UTF-8 编码，收发必须一致。波特率没有“默认正确”的值一般选择两边同时支持的最大值如 115200，每次接线都要核对。

## 接口约定先思考什么

以检测结果为例，先思考清楚：

```text
字段：class_id, u, v, angle
类型：uint8, int16, int16, float32
单位：u/v 为像素，angle 为度
坐标：左上角为原点，u 向右，v 向下
无目标：不发送，或发送约定状态值（二选一后固定）
频率：例如检测到新结果时发送
```

这六项每一项都对应一类联调错误：

**字段和顺序。** 文本格式按位置解析，接收方把第二个数当 `v` 还是当 `angle`，全靠这份约定。字段顺序改动一次，两边都要改。

**类型。** 文本格式里类型是“怎么转”的约定（收到 `"320"` 按整数解释）；二进制格式里类型直接决定字节数：`uint8` 占 1 字节、`int16` 占 2 字节、`float32` 占 4 字节，多字节还有排列顺序问题，见下文大小端。

**单位。** 发像素还是发毫米，要在[坐标标定](../04-坐标转换、标定与现场调试/01-坐标标定.md)之后再确认一次。可以发的是换算后的毫米值，如把距离乘 10 变成整数再发送（[2025 main.py](../../配套资源/历年题目参考代码/2025-TI杯视觉/main.py) 的发送字典），相当于用整数保留一位小数，接收端除以 10 还原。放大倍数必须一起约定，否则接收端会把 305 当成 30.5。

**坐标。** 图像坐标 u 向右、v 向下；换成机械坐标后原点和轴方向都变了（第 04 阶段的方向符号）。约定好如何“接收方按哪个坐标系解释这些数”。

**无目标。** 可以是：算不出有效值就把字段记为 `"0"`，任一字段为 `"0"` 就整条不发。也可以反过来，无目标时发送一个约定的无效状态值。两种都行，但要二选一后固定——“不发”意味着接收端要靠超时判断目标丢失，这也要提前说好。

**频率。** 两种模式：示例 [`MyUART.py`](../../配套资源/示例代码/maixpy/MyUART.py) 的发送线程每 20ms 发一次（最高约 50Hz，适合连续控制量，并且对于实时性更高的系统需要进一步提升）；2026年拼图题目是事件式，攒出一个完整动作才发。频率决定接收端多久收不到数据算异常。

## 三种格式分别长什么样

同一个检测结果 `class_id=1, u=320, v=224, angle=15.5`，三种编码各是什么样子、怎么解析、什么时候选它。

### 逗号分隔字符串

逗号只作为示例的分割符号，可以是其他符号，如 "+", "-"等符号，甚至是字母:"a","b"....

```text
1,320,224,15.50\r\n
```

教学版 [`protocol.py`](../../配套资源/示例代码/通信与gcode/protocol.py) 的编码是 `f"{int(class_id)},{int(u)},{int(v)},{float(angle):.2f}\r\n"`：逗号分字段，`\r\n` 结尾，小数固定两位。接收方按行读、按逗号切、按位置转类型。串口助手里直接能看懂，是联调成本最低的格式。

真实代码里有一个定宽变体（示例 [`MyUART.py`](../../配套资源/示例代码/maixpy/MyUART.py)）：

```python
content = "AA{:03d}BB".format(int(spd_dif))
if len(content) == 7:
    self.serial0.write_str(content)
```

帧头 `AA`、帧尾 `BB`、中间定宽三位，`{:03d}` 把 `5` 补成 `005`。接收方固定切出中间三位；总长度不等于 7 就整条丢弃，长度本身成了最简单的校验。字符串格式的代价在这里也看得清楚：定宽意味着加一个字段、两边解析全要改；小数和负数的写法要提前说死——这个例子只装得下 -99~999 的整数。

### JSON

```json
{ "class_id": 1, "u": 320, "v": 224, "angle": 15.5 }
```

教学版用紧凑分隔符编码、换行结尾。2025年选取的方式更直接（[2025 MyUART.py](../../配套资源/历年题目参考代码/2025-TI杯视觉/MyUART.py)）：

```python
json_data = json.dumps(date_dict)  # 初始化数据为 json 格式
self.serial0.write_str(json_data)
```

注意 `json.dumps` 不会自动加换行，这段发送没有任何终止符。那接收方怎么知道一条消息到哪里结束？由于是 json 格式，这里推荐使用接收回调靠内容定界（[2025 main.py](../../配套资源/历年题目参考代码/2025-TI杯视觉/main.py)）：

```python
# 进行字符切片获取到 {} 内的数据
left_start = all_str_data.find('{') if all_str_data.find('{') > -1 else 0
right_end = (all_str_data.find('}') + 1)  if all_str_data.find('}') > -1 else 0
str_data = all_str_data[left_start: right_end]

dir_data = loads(str_data)  # json解析数据
```

从收到的字节里找 `{` 和 `}`，切出中间一段再解析，前后的杂字节不管——这是文本协议“靠定界符找帧”的直接用法。同一个回调里还有 `if queue.qsize() < 1: queue.put(result)`：队列里始终只保留一条指令，多出来的丢弃。控制端要的是“当前该执行的那一条”，不是历史积压。

JSON 的优点：字段自描述，双方对着字段名核对含义；以后加字段，旧解析忽略新字段即可，不破坏兼容。代价：字段名每条消息重复传一遍，是三种格式里最占空间的。

### 二进制帧

示例帧的结构：

```text
帧头(2) | 长度(2) | 命令(1) | 负载(N) | 校验和(1) | 帧尾(2)
```

把开头那组检测结果按 `struct.pack(">Bhhf", ...)` 打包成负载，整帧的实际字节是（命令取 `0x01`）：

```text
AA 55 | 00 0A | 01 | 01 01 40 00 E0 41 78 00 00 | DC | 0D 0A
帧头    长度   命令  负载（9 字节）                  校验  帧尾
```

负载 9 字节 = `class_id`(1) + `u`(2) + `v`(2) + `angle`(4)。对照字节看每个部件为什么存在：

- **定长字段按偏移切。** `u` 永远在负载偏移 1~2（0 起数，第 0 字节是 `class_id`），`01 40` 就是大端的 320。解析不需要找分隔符，切偏移就行，这是二进制解析快、体积小的来源。
- **长度字段让帧可变长。** 它统计命令加负载共 10 字节（`00 0A`）。不同命令的负载不同，接收方先读长度，才知道要等多少字节。
- **大小端必须约定。** 320 大端是 `01 40`，小端是 `40 01`，错着解释就是完全不同的数。网络协议惯用大端，不少微控制器内存是小端；哪种都行，关键是收发一致。教学编码器和解析器都提供 `endian` 参数；示例 [`MyUART.py`](../../配套资源/示例代码/maixpy/MyUART.py) 的短帧用 `pack(">h", angle_tmp)` 发的是大端，而且发文本用 `write_str`、发原始字节用 `write`，是两个不同的接口。
- **那个短帧还演示了一个省字节技巧：** `angle_tmp = int(angle * 100)`，角度放大 100 倍存进 int16，接收端除以 100 还原。2 字节带上两位小数，绕开了浮点格式；边界是角度不能超过 ±327.67（和我们实际情况相关）。
- **校验和。** 命令加负载逐字节求和取低 8 位，写在帧尾前。它能查出一部分传输错误，也存在查不出的组合；更强的校验要用 CRC，但一般对于我们这样的简单系统不需要如此强的校验，甚至即使是现在推荐的校验和的方式也可以省去，只保留帧头帧尾和中间的内容负载。

### 三种格式的取舍

同一组值、各自带定界，整条消息的实际长度（运行 [`protocol.py`](../../配套资源/示例代码/通信与gcode/protocol.py) 可验证）：

| 编码       | 整条长度 | 直接可读     | 接收端解析             |
| ---------- | -------- | ------------ | ---------------------- |
| 逗号字符串 | 17 字节  | 是           | 找行尾、切逗号、转类型 |
| JSON       | 44 字节  | 是           | 找 `{}`、`loads`       |
| 二进制帧   | 17 字节  | 否，要看 hex | 找帧头、按偏移切       |

一个和直觉相反的结论：这条 4 字段的小消息里，二进制帧并不比字符串省——帧头、长度、校验、帧尾共 8 字节的开销，抵消了紧凑编码的优势（这里讨论的是不只保留帧头帧尾的情况）。二进制的收益要在字段更多、发送频率更高时才显现。JSON 最占空间，因为字段名每条都重复传。

真实项目是这么选的：2025 视觉端发 JSON——字段少，双方对着字段名确认含义最省事；2026 发 G-code 文本——执行端本来就按行执行 G-code，格式由需求决定。

## 半包和粘包：解析器为什么必须带缓冲区

串口读取返回的是“当前收到的若干字节”，读取时机和到达时机对不上，于是有两种必然出现的情况：

- **半包**：一条消息分几次到达。某次只读到 3 个字节，只是因为那 3 个字节先到。
- **粘包**：两条消息一次读出。缓冲里攒着上一条的后半段和下一条的开头。

这两种不是错误，是字节流的正常行为。应对方式是把读到的字节追加进缓冲区，解析器在缓冲区上循环：

```text
找帧头 → 按长度等整帧 → 校验 → 取出一帧 → 用剩余字节继续找
```

[`protocol.py`](../../配套资源/示例代码/通信与gcode/protocol.py) 的 `BinaryFrameParser.feed()` 实现了这个循环，包括两个容易漏的细节：

- **重同步。** 帧尾对不上或校验失败时，丢掉缓冲区第一个字节，重新找帧头。宁可丢一帧，也不能停在错误位置反复解析同一段坏数据。
- **半个帧头。** 缓冲区末尾只剩 `AA` 一个字节时先留着——它可能是下一个帧头的前半段。

测试对这两种行为都有断言（[`test_protocol_and_coordinate.py`](../../配套资源/示例代码/通信与gcode/test_protocol_and_coordinate.py)）：一帧只喂前 3 个字节时返回空列表，补上剩余字节再拼一帧完整数据后，两帧都被正确解出；校验和被改坏一个字节的帧会被丢弃，紧随其后的好帧照常解出。文本协议同理：按行读的解析器也要缓冲，读到没有换行就先存着；2025 的花括号切片就是文本版的“找帧头”。

## 实际项目的文本包（2026）

2026 代码实际发送的是这样的包：

```text
EEEF\r\n
G1 ...\r\n
M400\r\n
FFFE\r\n
```

`EEEF\r\n` 和 `FFFE\r\n` 是首尾定界符，思路和 `AA...BB` 一样，只是包住的不是一组数值，而是一个“语义块”。块按同步指令切：[`my_utils.py`](../../配套资源/历年题目参考代码/2026-拼图视觉/my_utils.py) 的 `_split_safe_blocks()` 在 `M400` 或 `G4` 后结束一块，保证移动指令和它后面的 `M400` 不被拆开——每块都是完整的语义单元（“移动到某处并等它到位”）。

块和块之间有节奏。发送一块后，等“这一块估算执行时间 × 1.5，再加至少 400ms”才发下一块，让下位机缓冲区任何时刻不超过一块。原因是：把整段程序一次性写进串口很容易，但接收端的缓存和执行速度不会因此变快——写入成功不代表消费得动。

这个真实协议没有长度字段，也没有校验和。可靠性来自三点：G-code 行本身人可读、块间有等待、和队友当面确认过这套约定。

## 上手练习

```powershell
Set-Location 配套资源\示例代码\通信与gcode
python protocol.py
python -m unittest test_protocol_and_coordinate.py
```

1. 跑 `protocol.py` 的 demo，看同一个值的三种编码各输出什么；demo 里二进制帧被拆成 4 字节加其余一段分别喂进解析器。
2. 读 `test_protocol_and_coordinate.py` 的断言，确认半包、粘包、坏校验和三种行为的预期结果。
3. 给接口约定加一个 `conf` 字段：三种编码各改一遍，再让测试通过。
4. 把 demo 的分段点从 4 字节改成 1 字节和半帧处，验证解析器仍能恢复。
5. 和控制同学各写一份六项接口约定，互相找出对方没写清的一项——通常是单位或无目标状态。

## 做到什么算学会

- 能向控制同学解释：为什么视觉端一次 `write` 不等于接收端一次 `read` 拿到一条完整消息，你们的协议靠什么从字节流里切出一条。
- 能说出自己选的格式牺牲了什么：体积、可读性、接收端工作量，至少两项。
- 联调看到“数据时对时错”，先查半包/粘包和缓冲解析，再怀疑算法。
