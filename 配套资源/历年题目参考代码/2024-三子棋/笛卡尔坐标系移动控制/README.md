# 2024 三子棋：坐标输出版

> 这是 2024 年往年题目的参考代码。它记录的是“视觉端输出移动坐标，控制端负责驱动机械”的完整分工，不是本人 2024 年的参赛项目。

这一版的最终交付物不是电机脉冲，也不是关节角或 G-code，而是一组带有明确起点和终点的坐标：

```json
{"from": [33.0, 15.0], "to": [130, 151]}
```

`from` 表示从哪里拿棋，`to` 表示把棋放到哪里。视觉端负责证明这两个点来自正确的棋盘、棋子和题目逻辑；收到 JSON 的控制端再决定怎样把坐标转换成机械运动。

## 数据怎样走完整条链路

### 1. 启动时建立棋盘坐标

[main.py](main.py#L52) 中的 `BaseInfo.find_board()` 会在启动阶段持续读取画面，裁剪出 `(80, 40, 160, 160)` 的棋盘区域，并在约 5 秒内累加多次九宫格检测结果。只有得到可用的 3×3 中心点后，程序才计算平均坐标。

这一阶段的输出不是“棋盘上有什么棋”，而是九个格子的稳定中心位置。后续题目逻辑只要知道目标格的行列，就能从这组中心点中取出对应像素坐标。

### 2. 每帧更新黑白棋子位置

[main.py](main.py#L24) 中的 `find_chess_info()` 分别查找黑棋和白棋中心，返回：

```python
{
    "black_chess": [...],
    "white_chess": [...]
}
```

主循环把这两组实时坐标与启动阶段保存的棋盘中心合并。执行对弈任务时，棋子中心还会映射为 3×3 逻辑棋盘中的行、列和棋子类别。

### 3. 串口指令选择题目逻辑

[main.py](main.py#L118) 的 `data_processing()` 负责接收并解析指令，再把有效任务放入队列。主循环根据字典中的键选择分支：

- `scan`：重新扫描棋盘；
- `one`：把一颗黑棋放到中心格；
- `two`、`three`：按指定颜色和格号放棋；
- `four`：处理一方先手的人机博弈；
- `five`、`six`：处理另一方先手的棋局。

队列把“收到命令”和“在主循环里使用最新画面执行命令”分开，避免在串口接收回调里直接完成整套视觉和博弈流程。

### 4. 题目逻辑生成 `from` 和 `to`

[topic_request.py](topic_request.py#L14) 的 `SerialNumber` 按小题组织动作。简单任务直接从棋子列表和棋盘中心取坐标；对弈任务先调用 [my_game.py](my_game.py#L21) 更新逻辑棋盘、检查局面并选择下一步。

博弈模块内部使用的是 `(row, col)`，机械需要的却是画面坐标。[topic_request.py](topic_request.py#L108) 的 `convert()` 在返回前完成最后一步转换：

- 如果 `from` 是棋盘外的待取棋子，就使用放置区中的棋子中心；
- 如果 `from` 是棋盘内已有棋子，就用行列索引换成对应格子的中心；
- `to` 始终从目标行列换成目标格中心。

到这里，题目编号、棋盘状态和 AI 决策都已经收敛为统一的点对接口。

### 5. 修正坐标并发送 JSON

[my_utils.py](my_utils.py#L9) 的 `sending_coordinate_data()` 是这一版的输出边界。它依次完成：

1. 对 `from`、`to` 调用同一个坐标修正函数；
2. 用 `json.dumps()` 编码点对；
3. 通过 `/dev/ttyS0`、115200 波特率写出字符串。

按当前 [alter_coordinate()](my_utils.py#L45) 的实际代码，X 会减去 `X_ERROR`，Y 最终仍采用原值。这里传出的坐标仍然与相机画面和现场约定有关，不能只根据字段名判断它已经是毫米坐标。

## 这版把什么留给控制端

坐标输出版不需要知道机械是直角坐标平台、SCARA 还是其他机构。视觉端交付的是“从 A 到 B”，控制端仍需负责：

- 确认坐标单位、原点、轴方向和有效范围；
- 把像素坐标换算成实际坐标（如果视觉端尚未完成）；
- 做机械逆解、限位、轨迹规划和速度控制；
- 执行拿棋、移动、放棋以及回零动作；
- 判断坐标是否越界，以及动作是否真正完成。

这种边界便于分别调试视觉和机械。代价是双方必须提前约定清楚坐标语义，不能只说“发送 X、Y”而不说明它属于哪个坐标系。

## 文件怎样阅读

- [main.py](main.py)：相机、显示、串口回调、任务队列和主循环入口。
- [topic_request.py](topic_request.py)：把各小题的规则统一转换成 `from/to`。
- [my_game.py](my_game.py)：主流程实际使用的棋盘状态、落子判断、AI 决策和错误修正。
- [my_utils.py](my_utils.py)：坐标修正、JSON 编码和串口发送。
- [sort_coordinate.py](sort_coordinate.py)：九宫格倾斜时的坐标排序算法独立版本，便于单独阅读。
- [play_game.py](play_game.py)：博弈逻辑的独立运行/调试版本；主流程导入的是 `my_game.py`，不要把两者当成同时执行。
- [app.yaml](app.yaml)：MaixPy 应用清单，记录应用入口和打包文件。

建议阅读顺序是 `main.py → topic_request.py → my_game.py → my_utils.py`。先跟一遍 `from/to` 怎样产生，再单独看坐标排序和博弈试验脚本，比按文件名逐个浏览更容易理解。

## 运行前需要核对

- 使用与代码时期匹配的 MaixCAM / MaixPy 环境，并保持 `app.yaml` 声明的运行模块完整。
- 核对相机裁剪区域、棋盘与棋子阈值、格子排序方向，以及黑白棋放置区边界。
- 核对模型或传统视觉资源在设备上的实际路径。
- 确认 `/dev/ttyS0` 和 115200 波特率与接线、控制端一致。
- 先打印并检查 `from/to`，再连接机械执行；至少覆盖四角、中心和放置区坐标。
- 明确控制端收到的是 JSON 坐标，不是 G-code。若控制端期待逐行 G-code，应改用同级目录中的 [G-code 输出版](../G-Code控制逻辑/README.md)。
